# Desktop review fixes — 2026-10-09

Implemented the three must-fix and seven should-fix findings from the [desktop review](2026-10-09-desktop-review.md), plus serialized browsing and useful startup progress. The original review remains a record of the pre-fix behavior. No new application dependencies were added.

## Finding-to-change mapping

| Finding | Implementation |
| --- | --- |
| 1. Weak no-game shutdown proof | Removed the local no-request/provider-loading shortcut. Only the verified guest guard, frozen under its activity lock, can skip backup. Unknown activity uses verified backup; failed backup retains the VM. |
| 2. Lost uncertain creation identity | Persist a unique label before creation, mark the request, recover the exact label/ID, and report `CREATION_UNCONFIRMED` when the result remains unknown. Reopen/Refresh reconcile it; no automatic replacement rental. |
| 3. Play races restoration | Share one restoration promise, disable Play during restoration, and await its result before replacing job state. Lookup failure blocks Play instead of representing an empty account. |
| 4. Failed/unbounded frontend caches | Limit completed artwork to 32 entries or 8MiB of encoded characters; release offscreen card references. Keep two active image requests. Metadata retains at most 128 successful entries for 24 hours; failed/partial results are retryable on Refresh. |
| 5. Large dropdown exceeds viewport | Reuse the common positioned popup, search and viewport-sized pages with keyboard navigation. Small lists stay simple; no menu scrolling. |
| 6. Stale running state/dead watcher | Label running state as last confirmed, keep its timestamp, and reconcile on Refresh/window focus. Verify exact-label guest state when reachable. Use owned-process exit events alongside inotify; a one-second PID fallback applies only during active startup. |
| 7. Overlapping host requests | One active host lookup plus only the latest queued game choice. Older results cannot overwrite current cards. Local search, price, continent and sorting cause no provider request. |
| 8. Unbounded retired jobs | Remove only stopped jobs with dead owned worker/engine processes. Preserve at least 24 hours, then the newest 50 for up to 30 days. Never prune unresolved rental identities. |
| 9. Unbounded native reads | Capture at most 8MiB stdout and 64KiB stderr. Read-only commands have a 75-second inner deadline and 85-second outer deadline; Linux termination is confined to their isolated process group. Lifecycle operations have no read-only timeout and discard oversized event lines. |
| 10. Missing Windows desktop distribution | Windows workflow builds the native x64 executable and matching source/checksum descriptor before packaging. The packager rejects missing/mismatched binaries. Install/update includes the app, signed WebView2 bootstrapper setup and GUI shortcut, preserving coordinated rollback/account data. |

## Startup progress

The existing engine remains authoritative. Verified guest progress is normalized into five stages: boot, game restore, runtime preparation, save restore and game start. Multipart restore already sums all parts; the UI consumes its whole-task bytes and total instead of chunk counts. Legacy transfer reporting no longer substitutes a single-file measurement when the task total is unknown.

Transfer percentage uses completed bytes divided by the whole task total. ETA is remaining bytes divided by measured throughput, shown only while startup is active and the measurement is no more than ten seconds old. Finishing transfer does not imply restore completion: verification/extraction may continue. Boot, runtime and overall completion have no invented ETA.

Progress travels through the existing fixed CLI command, private job record and Tauri event channel. It survives reopening and updates the game's neutral progress card. Its display timer stops when startup ends. Logs remain capped/redacted and their reserved slot does not collapse the banner when toggled.

## Cleanup and ownership

The shared command runner, launch controller, dropdown/popup and catalog caches own these behaviors. There is no additional daemon, database, router, UI framework or second scorer. Existing exact-offer quoting, lifecycle locks, immutable manifests, protected saves and provider-confirmed destruction remain in the shared engine.

Contributor rules and the [desktop architecture README](../../desktop/README.md) now describe the implemented behavior. Empty tabs and inactive game-settings controls remain deliberate placeholders.

## Validation and limits

The final Linux production frontend and native executable built successfully. Output: 127.72kB JavaScript (45.66kB gzip) and 22.81kB CSS (4.67kB gzip), excluding separate flag assets. The executable is `desktop/src-tauri/target/release/vastgame-desktop`. A build compiles Rust/Svelte output; it does not prove all TypeScript contracts, UI layout, race behavior or VM/save integration.

Focused regression fixtures were added for protected shutdown with unreachable proof, exact-label creation recovery, restoration lookup failure, retired-job retention, worker exit, whole-task progress/fresh ETA and matched Windows packaging. Tests, typechecks and lint were not run, as requested. No paid launches, shutdowns, backups or live provider probes were performed.

The Windows workflow, installer/update behavior and native Windows app have not been executed here. No new GitHub release or commit was created. The pipeline is prepared for a future manual artifact build or tagged release.

Unknown/unreachable game activity deliberately retains save protection; an unverified backup can leave a VM running and billing. Status is last confirmed rather than a continuous monitoring promise. Unresolved jobs are retained even beyond normal history limits. Older unknown creations without a persisted label cannot be reconstructed safely from guesswork.
