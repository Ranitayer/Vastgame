# Vastgame review — 8 October 2026

What this repo does: Vastgame rents a GPU VM, restores a packaged Windows game and its state, prepares Wine/Proton, and connects Moonlight through Tailscale. Linux and Windows share the manager and VM runtime. This review assumes one operator per computer, concurrent ingestion and gaming, and occasional use from a second computer sharing the same cloud accounts.

The modular monolith is a sensible architecture for this workload. Keep it. The highest-value work is correcting lifecycle boundaries and recovery, rather than another folder reorganization.

This was a source review, with read-only provider diagnostics for instance 54890066. No test suite or fresh rental was run. Only the startup changes described below were implemented. Other findings remain recommendations.

## Follow-up implementation

After this review, findings 4–6 were fixed in source: state operations retain the
VM manifest and verify its checksum under the guest state lock; a versioned,
verified state helper runs separately from the active runtime; ordinary backup
cleans up its temporary block on failure. Final-stop protection remains until
retry or explicit `vastgame state resume <game-id>`.

Finding 15 now has `vastgame cleanup` (preview) and `--apply`, protected retention,
process/build checks, and bounded HUD logs. The preview found no eligible artifacts
and deleted nothing. The former 24 GB workspace was already gone when cleanup was
implemented. Other review findings remain recommendations. No general refactor or
mass deletion was performed. These follow-ups passed syntax checks; tests were
added but not run, and no live VM was changed during implementation.

## Incident: instance 54890066

The saved and refetched evidence shows:

- The official Ubuntu CLI image finished pulling at 18:12:25 UTC, about 75 seconds after its pull started.
- Ubuntu booted and Vastgame began installing dependencies at 18:13:44 UTC.
- At 18:14:25 UTC, Vast began recreating the outer container. Further recreation attempts occurred approximately every two minutes.
- Later attempts stayed at `Preparing GPUs...`.
- At 18:25:45 UTC, the host reported `Error: GPU error, unable to start instance.`
- The report's saved status also contained that GPU error, with `actual_status=created` and `intended_status=stopped`.
- Both full-log requests had been rejected because they requested 100,000 lines; the API accepts at most 20,000.

This was not simply a slow game download or a Tailscale login delay. The guest briefly booted, then provider-side provisioning repeatedly restarted. The available logs do not reveal why the first guest was torn down, or the lower-level GPU reset/passthrough failure. Do not claim every previous rental had this same cause.

A configuration defect was independently confirmed: the selected Core template had `vm: false`, while the normal CLI rental path did not explicitly send `vm: true`. The existing custom-image API path did. The standard path now uses that same API helper with explicit VM mode, retaining the selected template's image and environment. This corrects the request, but a fresh rental is necessary to establish whether it resolves the observed restart loop. Vast's official API reference documents this field: https://github.com/vast-ai/docs/blob/main/api-reference/creating-instances-with-api.mdx

No existing VM was stopped, destroyed, restarted, or reconfigured. No new VM was rented.

## Must fix

1. **Explicit VM mode was missing from normal rentals — fixed in source.**
   What this is: `src/manager/launch.sh` submitted template-based rentals through the installed CLI, while `src/manager/create_vm.py` explicitly requested VM mode only for custom images.
   Problem: the selected template reported `vm: false`; the normal path relied on image/provider inference. Fix implemented: use the shared API helper with `vm: true` for both paths, omitting the image override for standard templates. This removes a launch ambiguity; live compatibility remains unverified.

2. **The failure report concealed the decisive GPU error — fixed in source.**
   What this is: `src/client/failure_report.py:163` chooses the cause displayed to the user.
   Problem: timeout classification returned before examining the saved status, and `--tail 100000` prevented host logs from being collected. Fix implemented: request 20,000 lines and prioritize a current explicit GPU error, including `instance.json` as evidence. Running status suppresses historical provider errors. Without this correction, the report directs users toward waiting when the host has reported a concrete failure.

3. **Planned stop hid real errors; stale text could reject running VMs — fixed in source.**
   What this is: `src/manager/provider.sh`, `check_instance_failure`, decides whether to stop watching.
   Problem: `intended_status=stopped` returned before examining explicit errors; the generic error-text check also applied to running guests. Fix implemented: inspect explicit errors for non-running guests, recognize the GPU error, and let running status override stale messages. A planned stop or missing domain alone still does not prove failure.

4. **Backup replaces the running VM's save policy before reading its saves.**
   What this is: `src/manager/persistence.sh:59` uploads the local manifest over the guest manifest before backup.
   Problem: another computer can have an older manifest or different save mappings. Required custom paths can disappear from the policy before the final backup, particularly for saves outside the prefix safety net. Fix: use the VM's launch-pinned manifest for backup; handle save-policy changes as explicit, validated migrations. Otherwise a verified upload can still omit the actual required save location.

5. **Stopping can overwrite runtime files while the game or checkpoint is using them.**
   What this is: `src/manager/persistence.sh:57` extracts the current local runtime directly into `/opt/vastgame` before acquiring the guest state lock.
   Problem: a live process can import a replacement helper while other modules remain from the earlier version; interrupted extraction can leave mixed files. Fix: stage a versioned helper bundle, validate it, and invoke the matching state tool under the existing guest coordination. Keep the active game runtime immutable. Otherwise backup itself can introduce a runtime failure.

6. **A failed ordinary backup leaves game launches blocked.**
   What this is: `src/runtime/game_state.py:657` creates the `stopping` marker before closing the game and uploading state.
   Problem: an upload or close failure bypasses marker cleanup, even for non-final `vastgame backup`. Launchers refuse to start while that marker exists. Fix: use exception-safe cleanup for non-final backups; preserve deliberate final-stop protection and provide an explicit recovery path. Otherwise a recoverable Drive failure can leave a paid VM unusable until manual repair.

7. **Windows updates can overlap an ingestion process.**
   What this is: `packaging/windows/update-backend.sh:16` acquires only `lifecycle.lock`; ingestion uses `catalog.lock` in `src/manager/commands.sh`.
   Problem: the updater can move the backend while ingestion still resolves helper paths from it. Fix: acquire both locks in the same order as normal catalog writers. Otherwise an import can fail midway despite the updater claiming no operation is active.

8. **Windows updates can leave a mixed installation after an error.**
   What this is: `packaging/windows/update-backend.sh:47` activates the backend before installing launchers/configuration; `Update-Vastgame.ps1:30` copies native files afterward.
   Problem: a later copy or disk-space failure does not roll the complete installation back. Fix: stage every component first, retain a transaction receipt, and restore all changed components on failure. Otherwise the error message says the update failed, but the installed files are already partly changed.

## Should fix

9. **A lost remote chunk makes cached publication retries fail repeatedly.**
   What this is: `src/client/package_publish.py:137` skips upload when its local journal says a chunk was verified.
   Problem: if that object was subsequently removed or moved during Drive repair, verification fails and the next attempt skips upload again. Fix: on a confirmed missing object, upload the available local chunk and verify again; preserve hard failure for ambiguous folders or conflicting content. Otherwise retained staging cannot repair the import by retrying.

10. **Windows updates unnecessarily require one particular game.**
    What this is: `packaging/windows/build_update.py` and `update-backend.sh:25` require a packaged Cyberpunk manifest.
    Problem: a user without Cyberpunk cannot build/apply a generic backend update. Fix: make game-profile delivery optional and separate from the backend update. Otherwise maintaining another user's installation depends on unrelated personal catalog data.

11. **Critical runtime dependencies still change between fresh VMs.**
    What this is: `src/bootstrap/start.sh` pulls Wolf `stable` and Lutris `edge`, and builds the preparation image from that moving Lutris tag.
    Problem: identical Vastgame source can receive different upstream binaries on different days. Fix: record and use tested image digests and resolved runtime versions per release. Keep updates deliberate. Otherwise an upstream change can break launch or MangoHud without any Vastgame code change.

12. **Ingestion rereads the entire ZIP unnecessarily.**
    What this is: `src/client/ingest.py:40`, `:96`, `:170`, and `:220` hash the downloaded archive.
    Problem: a cached retry hashes the ZIP in `download`, then hashes it again in `extract`; a trusted checksum adds another pass. Fix: return the just-verified digest from download and reuse it within that invocation, with archive identity/change checks. Do not remove integrity checking between separate invocations. This avoids multiple full reads of a 40–100 GB archive.

13. **Diagnostic generation still has fragile secondary steps.**
    What this is: `src/client/failure_report.py:219` awaits collector futures directly; history and timeline parsing later assume valid shapes.
    Problem: malformed history entries or a collector exception can prevent the final readable report from being written. Fix: isolate collector failures, validate optional history rows, and always emit a minimal summary. Also associate local Moonlight logs with the current session; the shared old log is presently copied unconditionally. Otherwise diagnosing one failure can produce another failure or stale evidence.

14. **The README contains operational claims that drift from implementation.**
    What this is: README and `docs/architecture.md` describe image selection, boot failures, and locks.
    Problem: the README still described a removed five-minute missing-domain abort and an enabled custom image; architecture documentation says local mutations share one lock despite ingestion's separate lock. The incident-related README text was corrected during this work. Finish the lock documentation and add an installed-version/runtime-version diagnostic. Otherwise users follow obsolete behavior when troubleshooting.

## Nice to have

15. **Large disposable artifacts lack a clear cleanup lifecycle.**
    What this is: the local `build/` directory occupies approximately 24 GB; `src/` is only 2.7 MB and tests 244 KB. HUD metrics append to per-session JSONL files, and Windows keeps backend backup directories.
    Problem: retained builds, session files, and update backups accumulate, making the project appear much larger than its source. Fix: add an explicit cleanup command with a preview, active-process checks, and bounded retention. Preserve save snapshots, credentials, current releases, and one recovery backend. No files were deleted during this review.

## What is already sound

- Keep the modular monolith and shared Linux/Windows backend.
- Package publication verifies chunks and publishes commit metadata before selecting the new manifest.
- ZIP extraction rejects traversal, links, duplicate paths, and unsafe entry types.
- VM identity uses contract IDs and launch labels rather than a shared hostname alone.
- Final shutdown retains the VM when backup cannot be confirmed and checks destruction separately.
- Missing game FPS is not replaced with Moonlight stream FPS.
- The test tree contains targeted persistence, state-lock, provider, packaging, and Windows regression cases. Their current pass status was not established here.

## Validation and priority

Changed Python files passed AST parsing; changed shell files passed shell syntax checks. Added regression cases cover explicit VM requests, current GPU errors during planned stop, and stale errors on running guests. Tests were not executed, as requested. The saved incident report was recollected using valid log limits.

Next order: validate one new rental with explicit VM mode, then address findings 4–8 before broad distribution. Follow with retry repair, generic updates, and pinned runtimes. Improvements 12–15 reduce time and maintenance cost without changing architecture.

Verdict: useful foundations, but not yet a fully verified release. Correct launch mode is now explicit; persistence/update boundaries are the remaining highest-risk areas.

Lean: roughly 24 GB of local build artifacts may be reclaimable after checking which outputs are still needed. No defensible line-count saving was measured; no new dependency is required for these recommendations.

Not checked: fresh GPU passthrough/streaming, actual Windows execution, live save restore, all native C++ paths, and every Core image build step. No code review can establish the physical host's hidden GPU teardown cause without provider-side evidence.
